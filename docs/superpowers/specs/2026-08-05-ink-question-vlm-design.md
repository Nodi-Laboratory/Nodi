# 펜으로 그려서 묻기 — 표시·손글씨·카드를 함께 읽는다 (D178)

작성 2026-08-05. 사용자 지시로 확정.

D176이 만든 것은 **손글씨 → 글자**였다. 학생이 캔버스에 쓴 획을 OCR로 읽어
입력창에 넣는다. 그런데 학생이 실제로 하는 일은 그것만이 아니다 — **카드를
동그라미 치고, 화살표를 긋고, 그 화살표 끝에 질문을 쓴다.** 지금 그 화살표는
아무 데도 전달되지 않는다. "이거에 대해서 더 자세하게 설명해줘"만 SOLAR에
도착하고, **"이거"가 무엇인지는 사라진다.**

이 문서는 그 "이거"를 살려 보내는 방법을 정한다.

## 무엇을 만드나

학생이 질문하는 펜으로 캔버스에 표시를 하고 [AI에게 묻기]를 누르면:

1. 질문 획들의 bbox를 잡고, **주변 카드를 끌어와** 상자를 넓힌다
2. 그림 두 종류를 만든다 — OCR용(획만) · VLM용(도식)
3. OCR과 VLM을 **동시에** 돌린다
4. 결과를 병합해 SOLAR에 넘긴다

핵심은 **두 모델에게 다른 그림을 준다**는 것이다. 목적이 다르기 때문이다:
OCR은 손글씨를 읽고, VLM은 표시가 무엇을 가리키는지 읽는다.

## 왜 그림을 나누나

OCR에 카드가 들어가면 **카드 본문까지 읽어 온다.** 그러면 어디까지가 학생의
질문이고 어디부터가 카드 내용인지 가르는 일이 새로 생긴다 — 그 분리는 신뢰할
수 없고, 틀리면 학생이 쓰지 않은 문장이 질문이 된다.

VLM에 카드가 빠지면 **화살표가 허공을 가리킨다.** 가리킨 대상이 그림에 없는데
"무엇을 가리키나"를 물을 수 없다.

그래서 OCR 그림에는 질문 획만, VLM 그림에는 질문 획 + 카드가 들어간다.
**둘 다 다른 펜으로 그린 그림은 빠진다** — 그건 어느 쪽에도 노이즈다.

D176의 `renderInkPng`이 이미 OCR 쪽을 만족한다. 화면을 캡처하는 것이 아니라
**획 좌표에서 새로 그리기** 때문에 카드도 다른 펜도 애초에 들어갈 수가 없다.
이 파일은 손대지 않는다.

## VLM 그림은 화면 캡처가 아니라 도식이다

`html2canvas`류로 화면을 캡처하는 길을 버렸다. 이유 셋 중 첫째가 결정적이다.

**화면 캡처는 뷰포트에 갇힌다.** 패딩으로 끌어온 카드가 화면 밖에 있으면
캡처할 방법이 없다. 그런데 카드를 끌어오는 기준은 "획 주변"이지 "화면 안"이
아니다 — 축소해서 보다가 화살표를 그으면 대상 카드가 화면 밖일 수 있다.
도식은 월드 좌표로 그리므로 이 문제가 성립하지 않는다.

나머지 둘: 자체 호스팅 손글씨 woff2 서브셋(524KB)을 인라인해야 해서 폰트가
깨지기 쉽고, Excalidraw 캔버스(z=2)와 DOM 오버레이(z=3)가 별도 레이어라 합성이
지저분하다. 느리기까지 하다(수백ms~수초).

**VLM에 필요한 것은 픽셀 충실도가 아니라 기하다.** 상자가 어디 있고 화살표가
어디서 어디로 가는지. 도식은 노이즈가 없어 오히려 잘 읽히고, "다른 펜 요소
제거"가 공짜가 된다 — 그릴 것만 그리므로.

### 그림 1: 전체 도식

```
┌─────────────────────────────────────┐
│  ┌──────────────┐   ╭─────────────╮ │
│  │① 천문학       │   │② 지질학      │ │  카드 = 월드 rect 그대로
│  │  본문…        │   │  본문…       │ │  번호 배지 + 제목 + 본문
│  └──────────────┘   ╰─────────────╯ │  (평범한 고딕. 손글씨 폰트 아님)
│                       ↖              │
│   이거에대해서더자세히  ╱               │  질문 획 = 빨강, 원래 좌표
└─────────────────────────────────────┘
```

**카드에 번호를 박는 것이 이 설계의 핵심 장치다.** VLM이 "②를 가리킨다"고
답하면 그 번호가 우리가 SOLAR에 보낸 카드 id와 1:1로 붙는다. 제목 문자열로
매칭하면 제목이 길거나 겹칠 때 어긋나고, 그 어긋남은 로그에도 화면에도 안
드러난다.

번호는 **읽는 순서**(위→아래, 같은 줄이면 왼→오른쪽)로 매긴다. VLM의 공간
추론과 번호 순서가 어긋나지 않게.

**색이 갈린다.** OCR 그림의 획은 검정(VARCO가 기대하는 형태), VLM 그림의 획은
**빨강**이다. 프롬프트가 "빨간 표시"라고 지칭할 수 있어야 카드 테두리와 섞이지
않는다. D176의 "화면과 전송본은 같은 획" 원칙은 OCR 쪽에 그대로 남는다 —
VLM 그림은 색이 의미를 나르는 별개의 도식이다.

### 그림 2: 도판 확대 (조건부)

표시가 **도판(`kind='figure'`)에 닿았을 때만** 보낸다. 도판을 원본 해상도로
놓고 **학생의 빨간 표시를 도판 좌표계로 다시 투영해** 같은 자리에 얹는다.
축척만 다른 같은 장면이다.

두 장을 다 주는 이유는 각자 못 하는 일이 있어서다. 도식만 주면 도판이
200px로 뭉개져 그림을 못 읽고, 확대본만 주면 화살표가 **어디서 왔는지**가
사라진다. 프롬프트가 "두 번째 그림은 ②번 도판을 크게 본 것이며 빨간 표시의
위치는 첫 번째 그림과 같다"고 못 박는다.

도판이 안 걸린 흔한 경우에는 그림 2를 아예 안 보낸다 — **비용이 지금 그대로다.**

닿은 도판이 둘 이상이면 **겹침 면적이 가장 큰 하나만.** 전부 보내면 비용이
선형으로 늘고, 화살표는 보통 하나를 가리킨다.

강의 클립(`kind='clip'`)은 제목 상자로만 그린다 — EBS 링크 카드라 읽을 그림이
없다.

## 카드 선정 알고리즘

"주변에 카드가 있으면 포함되게 패딩을 씌운다"를 그대로 구현하면 **폭주한다.**
상자를 키우면 새 카드가 들어오고, 그걸 포함하려 또 키우고, 조밀한 캔버스에서는
결국 전체를 삼킨다.

### 불변식: 선정은 한 번뿐이다

**카드 선정은 원래 획 bbox 기준으로 딱 한 번 한다. 상자를 키운 결과로 카드를
다시 줍지 않는다.** 이것만으로 종료가 알고리즘의 성질이 된다(수렴의 결과가
아니라). D123이 배치에서 택한 것과 같은 태도다.

### 1단 — 접촉

획이 카드에 실제로 닿았나. **bbox가 아니라 획 자체로 판정한다.**

대각선 화살표의 bbox는 커다란 직사각형이다. bbox로 재면 화살표가 지나가지도
않은 양쪽 구석의 카드가 딸려 온다. 획의 **선분**이 카드의 패딩 상자(hover
박스 — 연결선이 쓰는 그것, D126)와 교차하는지를 본다.

동그라미 친 카드, 화살표가 관통한 카드, 글씨를 그 위에 쓴 카드가 여기 걸린다.

### 2단 — 근접

닿진 않았지만 획 bbox에서 `ink_near_pad`(월드 px, 기본 120) 안에 있는 카드.

화살표 없이 카드 옆에 질문만 쓰는 것이 **가장 흔한 사용법**이다. 이 단이
없으면 그 경우가 빈손이 된다.

### 상한과 순위

`ink_card_max`개(기본 5)까지. 1단 먼저, 그다음 2단을 획 bbox와의 거리 순.

카드가 많이 딸려 오면 SOLAR가 받는 본문이 부풀고 화살표의 의미가 묻힌다.
잘린 것은 로그에 남긴다 — 조용한 절단은 "다 봤다"로 읽힌다.

### 최종 상자

```
capture = clamp( inflate(획 bbox, EXPORT_PAD) ∪ 선정 카드 rect들 )
```

원본 bbox의 `ink_box_max_scale`배(기본 2.5)를 넘지 않게 자른다. **"완전히
포함될 필요 없음"이 여기서 살아난다** — 큰 카드는 걸치는 만큼만 보이면 된다.

클램프가 없으면 상자가 커진 만큼 이미지 배율이 줄어 **정작 화살표가 몇
픽셀로 뭉개진다**(한 변 상한이 있으므로). 이 기능이 안 되는 형태가 아니라
**그럴싸하게 틀리는** 형태다.

## 도판 합성 — 캔버스 오염이 실제 위험이다

도판을 `ctx.drawImage`로 그리는 순간 이것이 걸린다. 다른 출처의 이미지를 그린
캔버스는 오염돼 `toBlob`이 `SecurityError`를 던진다 — **그림이 안 나오는 게
아니라 내보내기가 통째로 실패한다.**

지금 도판은 `/api/files/blob/…?exp=&sig=`로 온다. 배포는
`NEXT_PUBLIC_API_BASE_URL=/api`라 같은 출처라서 문제가 없다. 그런데 **로컬에서
`http://localhost:8000/api`로 둔 개발자는 다른 출처가 되어 여기서만 깨진다.**
배포에서는 멀쩡한데 로컬에서만 나는 실패라 원인을 찾는 데 시간을 버린다.

`<img>`를 우회한다: **`fetch` + Authorization 헤더 → blob →
`createImageBitmap` → `drawImage`.** 우리가 바이트를 직접 들고 있으므로 오염이
성립하지 않는다.

그러려면 헤더를 실을 수 있는 창구가 필요하다. signed URL은 `<img>`용이라
(`<img src>`는 Authorization을 못 싣는다) 이 경로에 안 맞는다.
**`GET /api/files/figures/{id}/raw`** 를 낸다 — 로그인 인증 + RLS 재조회로
기존 규약을 그대로 따르고, 덤으로 **만료 재발급 문제(D167)가 이 경로에는
아예 없다.**

### 레터박스 — 눈으로 못 잡는 곳

`FigureItem`의 `<img>`는 `object-contain` + `max-h-64`다. 즉 아이템 상자와
그림의 **실제 표시 영역이 다르다** — 세로로 긴 도판은 좌우에, 가로로 긴
도판은 위아래에 빈 띠가 생긴다.

이걸 무시하고 아이템 rect에 그대로 매핑하면 **동그라미가 그림의 엉뚱한 데
얹힌다.** 그런데 결과물은 "그럴싸한 그림"이라 눈으로는 안 잡힌다.
`penPad`·`connector`가 기하를 lib으로 뺀 것과 같은 이유로, 이 변환은 순수
함수로 빼고 테스트로 못 박는다.

### 도판을 못 받으면

만료·삭제·네트워크 실패면 그 자리에 **라벨만 있는 상자**를 그리고 넘어간다.
도판 하나 때문에 질문 전체가 막히면 안 된다 — RAG 불변식과 같은 성질이다.

## VLM 프롬프트

JSON을 요구하지 않는다. 스키마를 물리면 실패 갈래가 하나 늘고, 우리가 필요한
것은 결국 **SOLAR에 그대로 넘길 한국어 한 문단**이다. 대신 형식을 두 줄로
못 박는다.

### 시스템

```
너는 학생이 학습 화면에 그린 표시를 읽는 도우미다.

화면에는 학습 카드가 번호가 붙은 상자로 그려져 있고, 학생이 **빨간 펜**으로
그린 표시(동그라미·화살표·밑줄·손글씨)가 얹혀 있다.

너의 일은 **빨간 표시가 무엇을 가리키는지**를 말하는 것 하나뿐이다.

지켜야 할 것:
- 카드 내용을 설명하지 마라. 요약도 하지 마라. 그건 다른 모델이 한다.
- 빨간 표시와 닿지 않은 카드는 **닿지 않았다고 명시해서 말하라.**
- 카드를 부를 때는 반드시 [카드 N] 형식으로 번호를 써라. 제목만 쓰지 마라.
- 확실하지 않으면 확실하지 않다고 말하라. 지어내지 마라.

출력은 정확히 두 줄이다:

가리킴: <화살표가 가리키는 카드 번호 하나. 없으면 '없음'>
설명: <빨간 표시가 무엇을 어떻게 가리키는지 한국어 2~4문장>
```

### 사용자 (텍스트 파트)

```
화면에 있는 카드:
1 = 천문학
2 = 지질학
3 = 생명공학

첫 번째 그림이 화면 전체다.
(도판 확대본이 있을 때만) 두 번째 그림은 [카드 2] 도판을 크게 본 것이다.
빨간 표시의 위치는 첫 번째 그림과 같다.
```

**카드 명부를 텍스트로도 주는 이유**: 이미지 속 작은 제목을 읽게 시키면
틀린다. 그림에서 풀 문제는 **기하뿐이다.**

### 기대 출력

```
가리킴: 2
설명: 화살표가 왼쪽 손글씨에서 시작해 [카드 2]를 가리킨다.
[카드 2]는 빨간 동그라미로 감싸져 있다.
[카드 1]과 [카드 3]은 빨간 표시와 닿지 않는다.
```

`가리킴:` 줄만 파싱한다(없거나 이상하면 `없음`). `설명:`은 **손대지 않고**
그대로 넘긴다.

### 세 지시가 각각 막는 것

- **"내용을 설명하지 마라"** — 없으면 VLM이 지질학을 요약하기 시작하고, 그
  요약이 SOLAR의 근거가 된다. **작은 모델의 요약이 큰 모델의 입력을 오염시킨다.**
- **"닿지 않은 카드는 닿지 않았다고 말하라"** — 긍정만 시키면 "지질학,
  천문학, 생명공학 카드가 있다"로 뭉뚱그리고, SOLAR가 셋 다 설명하려 든다.
  **부정 진술을 강제해야 배제가 된다.** 이 지시가 여러 카드 예외의 전부다.
- **"[카드 N] 형식"** — 번호가 없으면 id 매핑이 문자열 추측이 된다.

## 창구

```
POST /api/ink/interpret
Content-Type: multipart/form-data
  ink_png    (필수) 획만 그린 흰 종이 PNG — 지금 OCR로 가던 그것
  scene_png  (선택) 전체 도식 PNG
  figure_png (선택) 도판 확대 PNG
  cards      (선택) JSON [{"n":1,"item_id":"…","title":"천문학"}, …]
  lang       (선택) 기본 "ko"

200 → {
  "text": "이거에 대해서 더 자세하게 설명해줘",   # OCR
  "marks_note": "화살표가 [카드 2]를 …",          # VLM 설명. 실패하면 ""
  "pointed": 2 | null,                            # 가리킴 파싱 결과
  "confidence": null
}
```

OCR과 VLM을 `asyncio.gather`로 동시에 돌린다. **마침 GPU가 갈라져 있어
진짜로 병렬이다** — OCR은 GPU 1(VARCO), VLM은 GPU 0(llama.cpp EXAONE).

기존 `POST /api/ocr/handwriting`은 **살려 두되 화면은 안 부른다.** 계약과
테스트가 붙어 있어 지우지 않지만, 카드가 없는 경우도 새 창구가 똑같이
처리한다(도식이 안 오면 비전을 아예 안 부른다) — 클라이언트에 갈래를 둘
만들 이유가 없다.

그래서 프론트의 `recognizeHandwriting`은 **지웠다**(2026-08-05 구현 중 결정).
죽은 코드를 "폴백"이라 부르며 남기면 다음 사람이 그것이 살아 있는 경로인 줄
안다. `lib/api/ocr.ts`에는 오류 문구 규칙(`OcrNotReadyError`·
`ocrErrorMessage`)만 남고, 새 창구가 그것을 그대로 쓴다 — 문구가 갈리면 같은
기능이 다르게 말한다.

같은 이유로 `ask-ink.spec.ts`의 라우트 세 곳을 `/ink/interpret`으로 옮겼다.
**옮기기 전에 실제로 깨지는 것을 확인했다**(3건 통과 후 4번째에서 실패).

### 실패 정책

**VLM 실패가 질문을 막지 않는다.** RAG 불변식과 같은 성질이다.

| 무엇이 실패 | 결과 |
|---|---|
| VLM 타임아웃·오류·미설정 | `marks_note=""`, 질문은 OCR 텍스트 + 카드로 나간다 |
| 도판 바이트 못 받음 | 라벨 상자로 대체, 나머지는 그대로 |
| OCR 실패 | **질문이 막힌다.** 손글씨가 곧 질문이라 대체할 것이 없다 |
| OCR 빈 결과 | 200 + `text=""` — 화면이 "다시 써 볼까요"로 안내(D176 그대로) |

OCR만 다른 이유: 다른 둘은 **곁들이**고 OCR은 **질문 자체**다.

## SOLAR에 무엇이 가나

`ChatStreamBody`에 필드 하나를 더한다:

```python
class InkContext(BaseModel):
    marks_note: str = Field(default="", max_length=2000)
    card_ids: list[str] = Field(default_factory=list, max_length=8)
```

`question`은 **OCR 텍스트 그대로**다. 그래야 툴팁·저장된 `askedQuestion`이
학생이 쓴 것과 같다. 표시 해석을 question에 이어 붙이면 저장된 질문이 벽이 된다.

**카드 본문은 클라이언트가 보내지 않는다.** id만 보내고 서버가 `user_conn()`으로
다시 읽는다 — RLS가 소유권을 강제하는 기존 경로 그대로다(D104). 찾지 못한 id는
버린다. 클라이언트가 보낸 본문을 프롬프트에 그대로 넣는 것은 기존 신뢰 경계
규약과 결이 안 맞는다.

프롬프트 블록은 `session_context`에 하나 더 붙는다:

```
[화면에 그린 표시]
화살표가 [카드 2]를 가리킨다. [카드 2]는 빨간 동그라미로 감싸져 있다.
[카드 1]과 [카드 3]은 빨간 표시와 닿지 않는다.

[표시 주변의 카드]
[카드 1] 천문학: …본문…
[카드 2] 지질학: …본문…
[카드 3] 생명공학: …본문…
```

번호가 두 블록에서 같아야 한다 — 이 대응이 깨지면 SOLAR가 엉뚱한 카드를
설명하고, **그 답은 그럴싸해서 아무도 못 잡는다.**

## 노브 (D62)

`admin_console._SPECS`의 "손글씨 인식" 그룹에 붙인다. 단일 소유자는 `_SPECS`다(D113).

| 키 | 기본 | 뜻 |
|---|---|---|
| `ink_vlm_enabled` | true | 표시 해석 킬 스위치 |
| `ink_card_max` | 5 | 끌어올 카드 상한 |
| `ink_near_pad` | 120 | 근접 판정 반경(월드 px) |
| `ink_box_max_scale` | 2.5 | 상자가 원본 bbox의 몇 배까지 |
| `ink_figure_zoom_enabled` | true | 도판 확대본을 보낼지 |
| `ink_vlm_timeout_seconds` | 30 | VLM 한 건 상한 |
| `ink_card_body_max_chars` | 1200 | 카드당 SOLAR에 넣을 본문 길이 |
| `ink_scene_max_side` | 1280 | 도식 PNG 한 변 상한 |

`config.py` 기본값 + `db/03_app_settings.sql` 행을 함께 넣어야 콘솔에 뜬다.
부팅 시 `ensure_setting_rows()`가 빠진 행을 채운다.

## 지연

| 구간 | 추정 |
|---|---|
| 도식 렌더 + 인코딩 | 0.2~0.5초 |
| 업로드 | 0.1~0.3초 |
| OCR | 3~8초 |
| VLM (그림 1장) | 5~15초 |
| VLM (그림 2장, 도판) | 8~20초 |

OCR·VLM이 병렬이므로 총합은 **최악 20초**쯤. 렌더는 전체의 3% 미만이라 체감에
안 잡힌다.

**모르는 사실 하나**: EXAONE-4.5 비전이 입력을 고정 해상도로 줄이는지, 타일로
쪼개 고해상도를 받는지. 고정이면 그림 2가 **필수**고, 동적 타일링이면 도식
한 장을 크게 보내는 것으로 갈음할 수도 있다. **추측으로 정하지 않는다** —
구현 첫 단계에서 도판 하나로 양쪽을 실제로 물어 확인하고, 결과를 이 문서에
적는다.

## 테스트

**순수 함수부터.** 기하는 눈으로 검증할 수 없다 — 틀려도 그럴싸한 그림이 나온다.

- `inkScene`: 대각선 화살표가 구석 카드를 안 줍는다 · 카드 선정이 한 번만
  돈다(키운 상자로 재선정하지 않는다) · 상한을 넘으면 자르고 잘렸음을 알린다
  · 클램프가 배율을 지킨다
- `figureCrop`: `object-contain` 레터박스에서 표시가 제 자리에 얹힌다
  (세로 긴 도판·가로 긴 도판·정사각 각각)
- `ink_marks`: `가리킴:` 파싱(정상·없음·헛소리) · VLM 실패가 빈 note로
  강등된다 · 카드 명부 조립
- e2e: 카드 옆에 획을 긋고 [AI에게 묻기] → 보낸 payload에 `scene_png`와
  `card_ids`가 실린다

## 무엇을 안 하나 (YAGNI)

- **표시를 저장하지 않는다.** D176 그대로 — 글자가 되는 순간 씬에서 빠진다.
  입력 수단이지 남길 내용이 아니다.
- **VLM 판정 로그를 관리자 페이지에 붙이지 않는다.** 개념 연결(D172)은 왜
  떴는지 안 떴는지가 안 보여서 로그가 필요했다. 여기는 학생이 방금 그린
  것에 대한 즉답이라 결과가 바로 보인다. 필요해지면 그때 붙인다.
- **화살표 방향을 우리가 계산하지 않는다.** 획에서 화살촉을 찾아 각도를
  재는 기하를 짤 수 있지만, 그게 VLM에게 시킨 일이다. 둘 다 하면 서로
  어긋날 때 어느 쪽이 맞는지 정할 근거가 없다.
