## 2라운드 — 경합·수명주기 (진행 중)

시나리오를 먼저 쓰고, 그 안에서 깨질 만한 것을 찾는다.

### S1. 답이 오는 중에 대화방을 바꾼다
학생이 질문하고, 답이 스트리밍되는 동안 옆 대화방을 누른다.
- 스트림이 **옛 세션에** 카드를 저장하나, 새 세션에 저장하나?
- `abort`가 걸리나? 걸린다면 이미 만든 카드는?
- 착지(방금 넣은 규칙)와 스트림 초점이 다투나?

### S2. 답이 오는 중에 새로고침한다
- 저장 전에 끊기면 그 답은 사라지나? 반쯤 저장되나?

### S3. 같은 계정으로 두 탭을 연다
- 한 탭에서 카드를 지우고 다른 탭에서 그 카드를 끌면?
- 수화는 세션당 한 번(D147)인데 두 탭의 정본이 갈리나?

### S4. 학생이 카드를 지운 직후 교차 연결 워커가 그 카드를 집는다

- 프롬프트 트리 컨텍스트는 상한이 있다(확인함).

### S6. 파일을 올리는 중에 질문한다

## 4라운드 — 방을 여는 길에 붙은 군더더기

| 예측 | 확인 방법 | 결과 |
|---|---|---|
| 방을 바꿀 때 `GET /sessions/{id}`(nodes·messages)를 아무도 안 읽는다 | 요청 파형 실측 | **참.** 현대 세션은 `canvas_items`가 화면을 채운다. 캔버스 스냅샷이 빌 때만 켜도록 게이트 |
| 목록 hover 미리 받기가 **엉뚱한 것**을 데운다 | `prefetchSessionData` 읽기 | **참.** 세션 상세를 데우고 있었다. 방을 여는 데 쓰이는 것은 캔버스 스냅샷 |
| 구 세션(카드 0·노드 1)이 폴백으로 살아 있나 | API로만 턴을 돌려 그 모양을 만들고 브라우저로 열기 | **산다.** 카드가 뜬다 |

실측(카드 40장 방 전환): 요청 4건 → **3건**.

## 5라운드 — 스킬 카탈로그 (사용자가 특히 지목한 축)

| 예측 | 확인 방법 | 결과 |
|---|---|---|
| `has_concepts=bool(nodes)`는 "카드가 있나"가 아니다 | 카드 0장 방에서 인사 3턴 | **참.** 1턴 1030ms → 2턴 1770ms. 인사에도 노드가 생겨 개념 스킬 둘 + think가 열리고 판단 단계가 통째로 돌았다. 매 턴 **+720ms** |
| 카탈로그를 좁히는 조회 셋이 줄 서 있다 | 코드 읽기 | **참.** `asyncio.gather`로 묶음 |
| `list_session_concepts`는 이미 다른 것이 하는 일을 한다 | 같은 질문 5회, 도구 호출 기록 | **참.** 5회 전부 `list → get`. 태그 재사용은 tag_guide가 이미 보장(D135), 제목 발견은 라우터가 어차피 읽는 행에 있다 |
| CLAUDE.md의 "스킬 8종"이 지금과 맞나 | 레지스트리와 대조 | **틀렸다.** 실제 11종. 넷이 빠져 있었다 |
| "노브는 씨앗 SQL에 넣어야 콘솔에 뜬다" | 스펙 수 vs 콘솔 응답 | **틀렸다.** 스펙 67 · 씨앗 49인데 콘솔에는 67개가 다 뜬다(`missing_row`) |

실측(개념 카드 1장 방, 같은 질문 5회): 5.3~8.0초 → **4.0~7.3초**, 5회 중 4회가 도구 한 번.
카드 0장 방 2턴째: 1770ms → **800ms**.

## 6~7라운드 — 화면을 직접 몰고 다니기

| 예측 | 확인 방법 | 결과 |
|---|---|---|
| DB 질의가 카드 200장에서 무너진다 | RLS 켠 채 `EXPLAIN ANALYZE` | **아니다.** 3.8ms, 인덱스 적중. `accessible_session_ids()`는 STABLE이라 한 번만 돈다 |
| 보존 정리가 훑을 인덱스가 없다 | `pg_indexes` | **있다.** jobs(status,created_at)·crosslink_runs(created_at)·ai_logs(created_at) |
| Excalidraw 자체 UI가 우리 것과 겹쳐 보인다 | 화면 실측 | **아니다.** DOM에는 있지만 0×0이다 |
| 방을 열면 착지한 카드가 화면 밖에서 시작한다 | 레이어 transform과 좌표를 직접 읽어 식으로 대조 | **참, 그리고 뿌리가 깊었다.** 아래 참조 |
| 같은 분류로 이어 물으면 카드가 옆으로 퍼진다 | **진짜 턴 4번** | **아니다.** 한 열에 세로로 쌓인다(x종류 1·y 4단). 합성 카드는 `parent_item_id`가 없어 다르게 배치된다 — 하마터면 없는 문제를 고칠 뻔했다 |
| 개념 카드가 없는 방은 착지가 취소된다 | 학생 글만 있는 방 | **참.** 카메라가 앞 방 자리에 선다 |

### 착지 어긋남의 뿌리 — "고쳐진 것처럼 보이는" 두 단계

배치는 rAF 뒤에 돈다. 크기가 막 실측된 프레임에는 `sizes`는 진짜 값인데
`positions`는 **폴백 폭으로 잡은 옛 좌표**다. 착지는 방마다 한 번이라
하필 그 프레임에 날면 되돌릴 기회가 없다.

| 고친 단계 | 착지 카드의 왼쪽 변 |
|---|---|
| 막지 않음 | −122px |
| 대상 크기만 기다림 | −79px |
| 모든 크기를 기다림 | −79px (**안 변한다** — 그 프레임에도 크기는 다 있다) |
| 좌표가 그 크기를 반영할 때까지(`layout.settled`) | **617px, 안전 구역 안** |

숫자가 뿌리를 말해 줬다 — 폴백 폭 560으로 잡힌 자리는 x=7200, 실측 폭 484.7로
다시 잡힌 자리는 x=6597. 카메라는 7200으로 날았다.

**교훈:** 중간 두 단계는 어긋남을 줄여서 고쳐진 것처럼 보였다. 화면을 눈으로만
봤으면 거기서 멈췄을 것이다. 식으로 대조해야 뿌리에 닿는다.
