# PROCESS.md — 태스크 실행 프로세스

> **Manager 전용 문서.** 서브에이전트로 디스패치되었다면 이 문서를 실행하려
> 하지 마라 — 받은 브리프의 task만 수행한다 (루트 CLAUDE.md의 역할 가드 참조).

`docs/TASKS.md`의 작업을 **위에서부터 하나씩** 수행하는 방법을 정의한다.
누가(페르소나)는 `docs/AGENTS.md`, 무엇을(태스크)은 `docs/TASKS.md`,
지켜야 할 것(불변식·컨벤션)은 루트 `CLAUDE.md`가 규정하고, 이 문서는
**어떻게 진행하는가**를 규정한다.

## 역할과 모델

| 역할 | 모델 | 하는 일 |
|---|---|---|
| **Manager** | **Fable** (`claude-fable-5`, 메인 세션) | **구현 스펙과 계획을 직접 세운다** (에이전트에 위임하지 않음). TASKS.md의 큰 태스크를 작은 task로 분해, 브리프 작성, 병렬 에이전트 디스패치, 리뷰 게이트 운영, 진행 기록. **직접 구현하지 않는다.** |
| **병렬 에이전트** | **Opus 4.8** (`claude-opus-4-8`, Agent 도구 `model: "opus"`) | 위임받은 작은 task 1개를 수행 (백엔드 개발자·프론트엔드 개발자·리뷰어·프론트엔드 리뷰어 — 페르소나는 AGENTS.md를 따름). 서로 파일이 겹치지 않는 task들은 **동시에 병렬로** 실행된다. |

- Manager는 AGENTS.md의 **아키텍트 + 오케스트레이터** 페르소나를 겸한다.
  스펙(brainstorming)·계획(writing-plans)은 사용자와의 대화가 필요하므로
  Manager 전담이며, 에이전트는 승인된 계획의 브리프만 받아 일한다.
- 에이전트 디스패치 시 반드시 `model: "opus"`를 명시한다 (누락 시 세션 모델을
  상속해 정책 위반).
- 코드 읽기·탐색(분해 시 파일 경계 파악, 리뷰 패키지 준비 등)은 serena MCP를
  우선 사용한다 — 사용법·워크트리 주의사항은 `docs/AGENTS.md` '공통 도구' 참조.

## 실행 루프

TASKS.md의 미완료 태스크 중 **가장 위의 것 하나**를 잡고 아래를 반복한다:

```
0. 설계   구현 스펙(brainstorming)과 계획(writing-plans)은 Manager가 직접
          세운다 — 에이전트에 위임하지 않는다. 사용자 스펙 승인이 게이트.
1. 분해   Manager가 태스크를 **최대한 잘게** 쪼갠다 — "독립적으로 테스트·
          커밋 가능한 최소 단위"까지. 이때 task 간 파일이 서로소가 되도록
          경계를 잡아 **병렬 폭을 최대화**한다 (분해가 잘될수록 동시에 뛰는
          에이전트가 많아진다). task 간 파일 겹침은 표로 정리한다.
2. 브리프  작은 task마다 브리프 파일 작성 — 경로는 TASK 번호로 네임스페이스:
          .superpowers/sdd/task{TASK}-{n}-brief.md (예: task1-2-brief.md,
          이전 실행 잔재와 충돌 방지). 내용: 요구사항 전문 + 정확한 파일
          경로 + 이전 task가 만든 인터페이스 + 완료 기준. 에이전트는
          브리프만 보고 일할 수 있어야 한다.
          워크트리에는 untracked 파일이 없으므로 브리프 경로는 **메인 저장소
          절대경로**로 전달하고, 브리프가 참조하는 문서(AGENTS.md 페르소나
          섹션 등)도 절대경로로 적는다.
3. 디스패치 **각 에이전트는 병렬로 실행한다 — 병렬이 기본, 순차는 예외.**
          Manager는 에이전트를 많이 생성해 업무를 넓게 할당한다: 준비된
          task들을 한 메시지에 동시 디스패치하고, 같은 파일을 만지는
          task들만 예외적으로 순차 실행한다.
          **병렬 구현 그룹은 각자 다른 git 워크트리에서 작업한다**
          (Agent 도구 `isolation: "worktree"`) — index를 공유하지 않으므로
          커밋 경합·스테이징 혼입이 원천 차단되고, 전체 테스트 스위트도
          옆 에이전트의 미완성 편집과 격리된 채 돌릴 수 있다. 병렬 그룹 내
          커밋 파일은 서로소여야 회수 시 충돌이 없다 (회수 절차는 4. 게이트).
          **워크트리는 커밋된 파일만 체크아웃한다** (2026-07-14 실측) —
          gitignore된 `backend/.env`가 없으므로 백엔드 브리프에 "시작 시
          메인 저장소 `backend/.env`를 자기 워크트리로 복사" 지시를 포함한다
          (gitignore라 커밋 혼입 위험 없음). `frontend/node_modules`도 없다 —
          프론트 스모크는 회수 후 메인 저장소에서 한다 (4. 게이트 참조).
          **워크트리가 낡은 베이스로 생성될 수 있다** (2026-07-14 TASK 1에서
          6회 중 4회 실측) — 브리프에 베이스 검증을 필수로 넣고 디스패치
          프롬프트에 필요 베이스 sha를 명시한다:
          `git merge-base --is-ancestor <필요베이스> HEAD || git reset --hard <필요베이스>`.
          **격리 가드가 워크트리 에이전트의 메인 저장소 쓰기를 막는다** —
          보고서는 자기 워크트리 안 `.superpowers/sdd/` 미러 경로에 쓰게 하고,
          Manager가 회수(cherry-pick) 시점에 cp로 가져온다.
4. 게이트  그룹 구현 완료 → Manager가 각 워크트리의 커밋을 작업 브랜치로
          회수(cherry-pick)하고 워크트리 정리 → 회수된 커밋 범위로 리뷰
          패키지 생성(`first^..last`, task당 복수 커밋 가능 — 타 세션 커밋
          혼입 금지) → 리뷰어 에이전트(opus) 디스패치 → 스펙 준수 + 품질
          이중 판정. **프론트엔드 task의 `npx tsc --noEmit && npm run build`
          스모크는 이 시점에 메인 저장소 `frontend/`에서 실행한다**
          (워크트리에는 node_modules가 없음). 병렬로 끝난 task들의 리뷰도
          병렬 에이전트로 동시에 돌릴 수 있다.
          **프론트엔드를 변경한 task는 프론트엔드 리뷰어를 추가 게이트로
          세운다** — UX·UI 기준 + playwright-cli 실동작 확인(스크린샷 증거).
          diff만 보고 프론트 변경을 승인하지 않는다.
5. 수정   Critical/Important 발견 시 수정 에이전트(opus) 디스패치 → 재리뷰.
          수정은 회수가 끝난 **작업 브랜치(메인 저장소)에서** 수행한다
          (워크트리 불필요 — 같은 파일을 만지는 수정은 순차로). 재리뷰에서
          다시 문제가 나오면 또 수정 → 재리뷰를 반복하며, 루프가 닫힐 때까지
          해당 task는 완료로 표시하지 않는다.
          **반려 롤백**: 리뷰가 접근 자체를 반려해 수정으로 구제할 수 없으면
          fix-forward를 중단하고, 회수된 해당 task 커밋을
          `git revert first^..last`로 되돌린다 (범위 revert는 최신 커밋부터
          역순으로 적용된다). revert는 새 커밋을 쌓는 비파괴 작업이므로
          Manager가 스스로 수행한다 — 단 병렬 세션이 같은 브랜치를 공유하므로
          `reset`·히스토리 재작성은 금지(중단 규칙의 파괴적 작업). revert
          커밋 메시지는 `[fix]:` + 반려 사유 한 줄, 원장에도 반려 사유를
          기록한다. 이후 브리프를 반려 근거로 보강해 **새 에이전트·새
          워크트리로 재디스패치**한다 (안전 규칙 '에이전트 실패 처리'와 동일
          — 반려된 산출물을 이어받지 않는다). 반려 원인이 스펙·계획 자체의
          결함이면 재디스패치 대신 중단 규칙에 따라 사용자에게 에스컬레이션.
6. 기록   TASKS.md 체크박스 갱신 + 원장(.superpowers/sdd/progress.md)에
          한 줄 기록 (커밋 범위·리뷰 결과·미해결 minor).
```

## 마무리 단계

**큰 TASK 하나가 끝날 때마다** (실행 루프 종료 후 반드시 수행):

1. **검증** — 프론트엔드 리뷰어 에이전트로 해당 범위의 수동 시나리오를
   확인한다 (UI 플로우를 통해 백엔드 동작까지 end-to-end로 검증, 완료 선언 전
   `superpowers:verification-before-completion` — AGENTS.md '마무리 검증 겸임')
2. **문서 동기화** — TASKS.md 체크박스·결정 기록 갱신, 루트 `CLAUDE.md`의
   "⚠️ 미구현" 등 현실과 어긋나게 된 서술 수정 (안 하면 CLAUDE.md가
   다음 세션에게 거짓말을 하게 된다)
3. **원장 마감** — 해당 TASK의 커밋 범위·리뷰 결과·자율 결정 사항을 원장에 기록
4. 다음 TASK로 이동

**모든 TASK가 끝나면**:

1. 최종 브랜치 리뷰 — 리뷰어 에이전트에 전체 diff 패키지 전달
2. Critical/Important 발견 시 수정 에이전트 1명에게 전체 발견 목록을 모아
   위임 → 재리뷰
3. `superpowers:finishing-a-development-branch` — 머지/PR/유지는 사용자 선택
   (파괴적·비가역 작업이므로 여기서만 사용자에게 묻는다)

## 중단·에스컬레이션 규칙

**미해결 결정·미해결 검증은 Manager가 스스로 판단하고 진행한다.** TASKS.md의
"미해결 결정" 항목에 도달하면(예: 교과서 코드 정리 수위) 트레이드오프를 따져
적절히 결정하고, 결정 내용과 근거를 TASKS.md·원장에 한 줄로 기록한 뒤 멈추지
않고 계속 간다. git으로 되돌릴 수 있는 결정은 전부 이 범주다.
검증도 마찬가지다 — 검증 방식·통과 기준이 명시되어 있지 않으면 Manager(또는
리뷰어 에이전트)가 적절한 기준을 스스로 정해 검증하고, 기준과 결과를
기록한다. 검증 기준을 물으러 멈추지 않는다.

Manager가 사용자에게 묻고 멈추는 경우는 다음뿐이다:

- 실행 루프 0단계의 **스펙 승인** (태스크당 1회의 정규 게이트)
- 에이전트가 BLOCKED이고 컨텍스트 보강·재분해로도 풀리지 않을 때
- 계획 자체의 결함을 발견했을 때 (스펙과 코드 현실의 모순 등)
- 파괴적·비가역 작업 (히스토리 재작성, 데이터 삭제, 머지/푸시)

그 외에는 **묻지 않고 다음 태스크로 계속 진행**한다. 태스크 사이 "계속할까요?"
확인 금지.

## 완료 정의 (Definition of Done)

작은 task 하나가 끝났다고 말하려면 전부 충족해야 한다:

1. TDD 증거 (RED → GREEN 출력)가 보고서에 있다.
   **예외 — 코드 제거·정리 task**: RED→GREEN이 성립하지 않으므로 전체 스위트
   통과 + 제거 대상 심볼의 잔존 참조 검색(grep) 0건 증거로 대체한다.
2. 전체 백엔드 스위트 통과 — **자기 워크트리 안에서** 실행
   (`cd backend && python -m pytest tests/ -v`; 워크트리에는 `.venv`·`.env`가
   없으므로 메인 저장소 venv 인터프리터를 절대경로로 사용하고, 브리프의
   지시대로 시작 시 메인 저장소 `backend/.env`를 복사해 둔다:
   `<메인저장소>/backend/.venv/bin/python -m pytest tests/ -v`).
   **프론트엔드 task는 이 항목 대신** `npx tsc --noEmit && npm run build`
   스모크 통과 — 단 워크트리에는 node_modules가 없으므로 실행 위치는
   **회수 후 메인 저장소 `frontend/`** 이고 게이트 단계에서 확인한다
   (1번 TDD 증거도 스모크 통과 증거로 대체).
3. 리뷰어 승인 (스펙 ✅ + 품질 Approved, Critical/Important 0건)
4. 파일 단위 커밋 완료 (`[feat]:`/`[fix]:` + 한국어, 자기 파일만 add)
5. TASKS.md 체크박스·원장 갱신

## 검증 환경

프론트엔드 리뷰어가 앱을 구동할 때 (루트 `CLAUDE.md` '개발' 절, README
'로컬 실행' 참조):

- Qdrant: `docker compose up -d qdrant`
- 백엔드: `cd backend && uvicorn app.main:app --reload --port 8000` (`GET /health`)
- 프론트: `cd frontend && npm run dev` → http://localhost:3000
- 프론트 스모크: `cd frontend && npx tsc --noEmit && npm run build`
- 브라우저 자동화는 전역 `playwright-cli` 사용 (2026-07-14 설치 확인 —
  frontend 의존성이 아니므로 워크트리에서도 CLI 자체는 사용 가능). 착수 전
  가용성을 재확인하고, 미가용 시 `run`/`verify` 스킬로 앱 구동 + 수동 확인으로
  폴백한다 (폴백 사실을 보고서에 명시).
- **포트 충돌 폴백**: 병렬 세션·리뷰어가 동시에 앱을 띄워 8000/3000이 이미
  사용 중이면 다른 포트로 띄운다 — 백엔드 `--port 8001`, 프론트
  `npm run dev -- --port 3001`. 프론트는 `NEXT_PUBLIC_API_BASE_URL`이
  백엔드 포트를 가리키므로, 백엔드 포트를 바꿨다면 프론트 구동 시
  `NEXT_PUBLIC_API_BASE_URL=http://localhost:8001`을 함께 넘긴다.
- **검증 계정** (D99, 2026-07-27 갱신): 로그인은 **이메일/비밀번호**다
  (Google OAuth 제거). 로컬 스택의 `supabase/seed.sql`이 역할별 계정을 만들어
  두므로 브라우저 자동화도 그냥 로그인 폼을 채우면 된다 — 영속 프로필·쿠키
  주입 같은 우회가 더는 필요 없다.
  - 선생님 `teacher@nodi.local` / 학생 `student@nodi.local` /
    관리자 `admin@nodi.local` — 비밀번호는 전부 `nodi-local-dev`
  - 학급 "로컬 테스트 학급"(코드 `LOCAL1`)에 교사·학생이 이미 소속돼 있다.
  - 토큰이 직접 필요하면 `POST /auth/v1/token?grant_type=password`(anon 키)로
    받는다.

## 안전 규칙 (이 저장소 특수 사정)

- **병렬 세션**: 같은 브랜치에 다른 세션이 커밋할 수 있다. 리뷰 범위는 항상
  회수된 해당 task 커밋으로 한정하고, 낯선 커밋을 발견해도 건드리지 않는다.
- **미커밋 WIP**: 작업 트리에 이 작업과 무관한 미커밋 변경이 있을 수 있다.
  에이전트 브리프에 "자기 파일만 `git add`"를 항상 포함한다. 자기 파일에
  기존 WIP 훅이 섞여 있으면 보고서에 명시하고 진행한다.
- **에이전트 실패 처리**: 에이전트가 중도 실패하면(오류로 종료, 완료 기준
  미달 보고 등) 커밋 안 된 워크트리는 **폐기**하고, 실패 원인을 반영해
  브리프를 보강한 뒤 **새 에이전트로 재디스패치**한다. 미완 워크트리를
  이어받지 않는다 (이력 오염 방지).
- **원장 우선**: 컨텍스트가 요약·유실되면 자기 기억보다 원장과 `git log`를
  믿는다. 원장에 complete로 기록된 태스크는 재디스패치하지 않는다.
